# MCP Workbench Proxy architecture

## Supported product surface

One proxy process owns all configured stdio and Streamable HTTP upstreams.
Each upstream has two loopback endpoints:

- `/mcp/servers/{server_id}` exposes agent-visible Raw tools and publications.
- `/mcp/controller/{server_id}` exposes every Raw tool to the authenticated
  private controller, including tools hidden from agents.

Raw tool names, schemas, arguments, results, structured content, metadata and
protocol errors are forwarded without interpretation. `agent_hidden_tools`
only changes the agent catalog; `disabled_tools` remains an upstream filter.

The loopback management API uses an API key. Publication callbacks use a
separate bearer token generated by the private host. The proxy contains no
workflow discovery, agent-log analysis or proprietary workflow execution.

## Product build

The supported release target is Windows x64:

```powershell
go test ./internal/config ./internal/server ./internal/httpapi
go build -trimpath -o mcp-workbench-proxy.exe ./cmd/mcpproxy
```

The upstream tray, frontend, marketplace and search sources remain in the fork
to simplify upstream merges but are not built or supported by MCP Workbench.

## Compatibility contract

- Proxy configuration version: `2`.
- Agent endpoint: `/mcp/servers/{server_id}`.
- Controller endpoint: `/mcp/controller/{server_id}`.
- Management endpoints: `/api/v1/*` on loopback.
- Publication callbacks preserve the complete MCP result or protocol error
  returned by the private host.

Breaking changes require a versioned private-application migration before a
proxy release is published.
